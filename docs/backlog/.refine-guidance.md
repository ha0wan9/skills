# Project Board Refinement Guidance

Distilled from DASH-08 co-review sessions. Keep it small, current, and specific.

## Structural invariants (stable)

- Items are roadmap-eligible only when `maturity: refined` and `disposition: active`.
- Keep `maturity` about requirement quality; use `status` for execution state and
  `disposition` for trim/defer/wontfix decisions.
- Dedup is resolved at the roadmap single-writer gate (DASH-08), never at append-only capture.

## Current direction

- v0.1–v0.7 have **shipped**; milestones are capability bundles, not sequential sprints
  (v0.5 shipped while v0.4 stayed open — established precedent). Describe direction, not frozen scope.
- v0.8 (Harness self-audit + component upgrade) opened 2026-06-13: DASH-54 (dashboard Audit panel
  + CLI-recipe composer, P3 reuse/create-or-combine spike) + DASH-55 (`project-meta upgrade` CLI,
  net-new per-component version surface). Both refined-in-place as L; 55 sequences before 54
  (54's version-vs-latest health signal consumes 55's surface). **DEC-002 (per-component version +
  latest-on-git resolution) is OPEN and blocks DASH-55 scheduling.** Fleet-hygiene CI #2–#5 +
  token-diet D3–D5 stay pooled for v0.9.

## Acceptance-shape patterns that pass

- A refined item names a concrete, **self-checkable** acceptance shape — a CLI exit code, a
  gated invariant, an artifact field — not a vague outcome.
- Items that **reuse existing infra** (review-tier L0–L3, `board.py`, multi-agent-protocols)
  refine cleanly; net-new machinery draws scrutiny and usually wants a spike first.

## Acceptance-shape patterns that pass (additions, v0.6 session)

- **Size before scheduling.** All seven agentic-infra items arrived with empty `rough_size`;
  the L2 panel had no capacity signal. Proposal→item filing should stamp a rough size, or the
  roadmap gate does it (as v0.6 did: 5×S, 1×M scheduled; L stays pooled).
- Hook-payload items must name their **profile gating + wiring proof** (fragment block, not a
  comment) in the acceptance shape, or they risk shipping inert (AP-VAL-1).

## Acceptance-shape patterns that pass (additions, v0.8 session)

- **An OPEN at an item's technical core is a blocking decision row (DASH-027), not acceptance
  prose.** DASH-55 embedded "PLAN-TIME OPEN: how latest-on-git is resolved" inside its
  acceptance shape; the L2 panel (3/3) flagged it — an unresolved design question at the core
  belongs in the milestone `decisions[]` (it became DEC-002, blocking DASH-55), so the
  scheduling gate enforces it. Don't bury the bet in prose.
- **Condensing fuzzy→refined silently drops actionable clauses.** Refining DASH-54 dropped the
  operator's "create / combine on a SoTA gap" *action* down to a ranking display. Fix: a refined
  item that condenses a multi-clause fuzzy ask must carry a plan-time **completeness cross-check
  against the original wording**, and the L2 panel's usefulness lens must diff refined-vs-original
  intent.

## Recurring trim/staleness reasons

- Guidance pinned to a fixed version ceiling goes stale fast — describe **direction**, not a
  frozen scope. (This file's own v0.1 note was the example.)

## Operator deltas (structured)

co-review. Bounded to **≤10 rows**; merge rows that share a pattern; evict oldest when the bound
is reached. Raw session logs do not belong here — only the generalized pattern.

Schema: `{item, delta, reason-pattern}`
where `delta` ∈ {accepted-as-is, modified, defer-back, trim, spawn, reject}.
